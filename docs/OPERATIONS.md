# Защита и диагностика

Сервер ограничивает стоимость обработки входящих соединений и сигналинга. Это уменьшает ущерб от флуда HTTP/WebSocket и медленных TLS-клиентов. Атака, заполнившая канал хостинга до сервера, требует помощи провайдера: приложение не может освободить этот канал.

## Встроенные ограничения

| Ресурс | С одного IP | Всего |
| --- | --- | --- |
| Новые TCP-соединения | 30/с, всплеск 60 | 100/с, всплеск 200 |
| Открытые TCP-соединения | 128 | 2048 |
| HTTP-запросы | 60/с, всплеск 180 | 1000/с, всплеск 2000 |
| Входы в WebSocket | 2/с, всплеск 12 | 20/с, всплеск 40 |
| Одновременные WebSocket | 64 | 256 |

IPv6-адреса объединяются по /64. Учитывается адрес TCP-подключения, заголовок X-Forwarded-For не доверенный. За reverse proxy все клиенты будут делить его лимит: этот режим требует отдельного проектирования доверенных прокси. Несколько пользователей за NAT тоже делят лимит; массовое одновременное подключение может потребовать повторной попытки. Постоянных блокировок IP нет. HTTP возвращает 429 и Retry-After.

Одновременно обрабатываются не более 128 начальных TCP/TLS-подключений; очереди HTTPS/ICE/TURN ограничены 128. Начальное чтение и TLS имеют таймауты, заголовки HTTP ограничены 16 KiB. Для первого сообщения join разрешено 2 KiB и 10 секунд.

Каждый WebSocket допускает 30 сообщений/с (всплеск 120), 256 KiB/с (всплеск 512 KiB), не более 256 KiB в одном сообщении. Переговоры SDP/ICE restart ограничены 2/с со всплеском 8. Переполнение закрывает нарушающее соединение. Очередь участника ограничена 512 задачами. Существующие ограничения количества комнат и участников также действуют.

Медиапакеты UDP не ограничиваются этими HTTP/WS-лимитами: голос и высококачественная демонстрация используют отдельный путь. Это не полноценная защита от UDP-флуда. TURN требует авторизации и разрешает ретрансляцию только к SFU.

## Журнал приложения

Каждые 15 секунд stdout получает JSON `traffic_summary`: число запросов и ответов по классам, ошибки TLS, отказы лимитов, входы/выходы, активные TCP/WS и незавершённые handshake. Счётчики `counts` относятся к интервалу; `gauges` — текущее состояние. Имена комнат, IP, URL-параметры, ключи, пароли и сообщения в эти записи не входят. Публичного endpoint с метриками нет.

В Docker используйте `docker compose logs --since 30m`. Ротация уже задана в compose. Рост `http_429`, `tcp_rejected`, `ws_message_rejected`, `handshake_capacity_rejected` показывает срабатывание защиты, но сам по себе не доказывает DDoS.

## Дополнительный монитор Linux/systemd

`scripts/server-monitor.py` требует Python 3, читает /proc и раз в 15 секунд проверяет локальный HTTPS с проверкой сертификата домена. Он пишет трафик, потери, TCP/SYN, переполнения очередей, доступную память, load и результат HTTPS. IP и пакеты не сохраняются. `traffic_anomaly` отмечает >25 тысяч входящих пакетов/с, >100 Мбит/с, >=128 SYN_RECV или новые потери/переполнения. Большой легитимный звонок тоже может вызвать такой сигнал; сопоставляйте его с метриками приложения. Это журнал, без внешней отправки уведомлений.

Установка для systemd с поддержкой LogNamespace (245+):

```sh
sudo install -Dm755 scripts/server-monitor.py /usr/local/lib/audio.lgbt/server-monitor.py
sudo install -m644 deploy/audio.lgbt-monitor.service /etc/systemd/system/audio.lgbt-monitor.service
sudo install -m644 deploy/journald-audio-lgbt.conf /etc/systemd/journald@audio-lgbt.conf
sudo mkdir -p /etc/systemd/system/audio.lgbt.service.d
printf '[Service]\nLogNamespace=audio-lgbt\n' | sudo tee /etc/systemd/system/audio.lgbt.service.d/observability.conf
```

Измените `--domain` в service на свой домен. Основной unit здесь называется `audio.lgbt.service`. Затем:

```sh
sudo systemctl daemon-reload
sudo systemctl restart audio.lgbt
sudo systemctl enable --now audio.lgbt-monitor
sudo journalctl --namespace=audio-lgbt -u audio.lgbt -u audio.lgbt-monitor --since '30 minutes ago' -o cat
sudo journalctl --namespace=audio-lgbt --disk-usage
```

Журнал namespace ограничен примерно 100 MiB и 14 днями; активный файл может временно добавить до 10 MiB. Ограничение частоты защищает диск от потока внутренних ошибок. Старые записи основного сервиса остаются доступны обычным `journalctl -u audio.lgbt`.

При недоступности извне и успешном `local_https` ищите сетевую проблему, фильтрацию или атаку до сервера. Если трафик на сервер не дошёл, эти журналы его не покажут. Сохраните точный интервал UTC и попросите у хостинга графики входящего трафика, потерь и срабатываний анти-DDoS.
